# create-plan

> Generate a comprehensive, self-contained `plan.md` for a JIRA feature that already has a feature spec.

---

## Purpose

This workflow reads an existing feature spec (`ai/specs/{ISSUE_ID}/specs.md`), performs a deep-dive codebase analysis, and produces a detailed implementation plan at `ai/specs/{ISSUE_ID}/plan.md`. The plan is designed to be directly consumable by an AI coding agent (or a human developer) with zero additional context — every file path, method name, line range, test pattern, and constraint is spelled out explicitly.

---

## Prerequisites

- The JIRA issue ID (e.g. `PROJECT-1234`) must be provided as input.
- A feature spec must already exist at `ai/specs/{ISSUE_ID}/specs.md`. This is generated by the `create-specs` skill (step 1 in the Feature Development Lifecycle).
- POD-level specs must exist at `ai/knowledge/` (generated once by `create-pod-knowledge`):
  - `technical-spec.md`
  - `functional-spec.md`
  - `data-model-spec.md`
  - `api-spec.md`
  - `flows/*.md` (registration flow diagrams)
  - `data/*.json` (sample request/response payloads)
- `AGENTS.md` must exist at the workspace root (generated by the `create-pod-knowledge` skill).

---

## Workflow Steps

### Step 1 — Obtain JIRA Issue ID

Accept the JIRA Issue ID (e.g. `PROJECT-1234`) from the user invocation.

**Verify** that the feature spec file exists:

```
ai/specs/{ISSUE_ID}/specs.md
```

If the file does **not** exist, **stop immediately** and report:

```
ERROR: Feature spec not found at ai/specs/{ISSUE_ID}/specs.md
Run the create-specs skill first: /create-specs {ISSUE_ID}
```

Do not proceed without a feature spec — the implementation plan depends entirely on it.

---

### Step 2 — Read Feature Spec

Read the full contents of `ai/specs/{ISSUE_ID}/specs.md`.

**Extract and internalise the following sections** (section numbers may vary — match by heading text):

| What to Extract | Typical Section | Why |
|---|---|---|
| **Summary / Overview** | §1 or top-level | Understand the feature at a high level |
| **Functional Requirements (FRs)** | §2 or §3 | Every FR becomes a line item to implement |
| **Acceptance Criteria (ACs)** | §3 or §4 | Every AC becomes a test case |
| **Impacted Areas / Affected Services** | §4, §5, or §6 | Determines which projects and modules are in scope |
| **API Changes** | §5 or dedicated section | New endpoints, changed request/response shapes |
| **Data Model Changes** | §6 or dedicated section | New fields, new collections, index changes |
| **Open Questions** | §4.9, §7, or final section | Must be flagged in the plan — some may block implementation |
| **Example Request / Response** | Inline or references to `ai/knowledge/data/` | Critical for understanding expected behaviour |
| **Out of Scope** | Explicit exclusion section | Prevents scope creep — reference in "Files NOT to Modify" |

**Build a mental model** of:
- What the feature does (user-facing behaviour)
- What triggers it (API endpoint, event, scheduled job)
- What data it reads and writes
- What side effects it produces (messaging events, audit records, integration calls)
- What constraints apply (backward compatibility, performance, security)

---

### Step 2B — Resolve Open Questions & Assumptions Gate

Before generating the implementation plan, **all open questions and unverified assumptions in the feature spec must be closed**. An implementation plan built on unresolved ambiguities leads to rework.

#### 2B.1 — Extract open items

Parse the feature spec for:

1. **Open Questions** (typically §4.9 or a dedicated section) — any item not marked as `[RESOLVED]` or `[CLOSED]`.
2. **Auto-Resolved Assumptions** (marked `[AUTO-RESOLVED]`) — these were resolved by the AI during spec creation but have not been confirmed by a human.
3. **Inline TODOs or TBDs** — scan the full spec for any `TODO`, `TBD`, `TBC`, or `[OPEN]` markers.

#### 2B.2 — Evaluate closure status

Classify each item:

| Status | Meaning | Action |
|---|---|---|
| `[RESOLVED]` or `[CLOSED]` | Explicitly answered | ✅ No action needed |
| `[AUTO-RESOLVED]` | AI-answered, not human-confirmed | ⚠️ Present for confirmation |
| Open (no marker) | Unanswered | ❌ Must be answered before proceeding |
| `TODO` / `TBD` / `TBC` | Placeholder | ❌ Must be answered before proceeding |

#### 2B.3 — Gate decision

**If ALL items are resolved** → proceed to Step 3.

**If ANY items are open or unconfirmed** → present them to the user and **WAIT**:

```
=== Open Questions Gate — Cannot Proceed ===

The feature spec has {N} unresolved item(s) that must be closed before
I can generate a reliable implementation plan.

OPEN QUESTIONS (must be answered):
  Q1: {question text}
      Why it matters: {impact on implementation if answered wrong}
  Q2: {question text}
      Why it matters: {impact}

UNCONFIRMED ASSUMPTIONS (need your confirmation):
  A1: {assumption text} — Evidence: {source}
      → Reply "confirmed" or provide the correct answer
  A2: {assumption text} — Evidence: {source}
      → Reply "confirmed" or provide the correct answer

INLINE PLACEHOLDERS:
  - Section {X}: contains "TBD" at {location description}

Please answer the open questions and confirm/correct the assumptions.
I'll update the feature spec and then proceed with plan generation.
```

**WAIT for user response.**

#### 2B.4 — Update feature spec

After the user provides answers:

1. Update the Open Questions section in `specs.md` — mark each answered question as `[RESOLVED]` with the answer.
2. Update each `[AUTO-RESOLVED]` assumption to `[CONFIRMED]` or replace with the corrected answer.
3. Replace any `TODO`/`TBD`/`TBC` placeholders with the provided content.
4. Re-scan the spec to confirm zero open items remain.

If new questions surface from the user's answers (e.g., "that depends on X"), add them as new open questions and loop back to 2B.3. Continue until the spec has **zero unresolved items**.

#### 2B.5 — Log closure

```
=== All Open Questions Resolved ===

Resolved: {N} open questions, {N} assumptions confirmed
Feature spec updated: ai/specs/{ISSUE_ID}/specs.md

Proceeding to implementation plan generation.
```

### Step 2C — Constitution / Governance Check

Before generating the implementation plan, check whether a project constitution exists and load its governance principles. The constitution defines non-negotiable engineering principles that all plans must comply with.

#### 2C.1 — Locate the constitution

Check for `CONSTITUTION.md` in the `ai/` repository:

```
ai/harness/CONSTITUTION.md
```

If the file does not exist, skip this step silently and proceed to Step 3. The constitution is optional — teams that do not use one will not be affected.

#### 2C.2 — Parse governance principles

Read `ai/harness/CONSTITUTION.md` in full. Extract:

1. **Core Principles** — numbered or bulleted statements under a "Core Principles" or "Principles" heading. Each principle is a non-negotiable rule (e.g., "Spec-first: no code without a spec", "TDD: tests before implementation", "Backward compatibility: additive changes only").
2. **Quality Gates** — any explicit quality gates or checks listed (e.g., "All unit tests pass before push", "No secrets in code").
3. **Conventions** — version control conventions, branching strategies, naming rules, or patterns that constrain how the plan should be structured.
4. **Feature Development Standards** — required artefacts, JIRA integration rules, and human review checkpoints.

> **Note:** Technology stack is not governed by the constitution — it is captured in `AGENTS.md` (auto-generated from the codebase by `/create-pod-knowledge`). Use `AGENTS.md` for tech-stack alignment checks.

Store these as a governance context to be checked against during plan generation.

#### 2C.3 — Validate feature spec against constitution

Before generating the plan, verify the feature spec does not violate any constitution principles:

| Check | What to Verify | Action if Violated |
|---|---|---|
| **Principle compliance** | No FR or AC in the feature spec contradicts a core principle | Flag the conflict: `CONSTITUTION VIOLATION: FR-{N} contradicts principle "{principle}". Resolve before proceeding.` |
| **Technology alignment** | The feature spec's impacted areas and approach align with the technology stack documented in `AGENTS.md` | Flag misalignment: `CONSTITUTION WARNING: Feature uses {tech} which is not in the documented stack (see AGENTS.md).` |
| **Quality gate readiness** | The feature spec meets all prerequisite quality gates (e.g., has acceptance criteria if the constitution requires them) | Flag the gap: `CONSTITUTION GATE: Constitution requires {gate} but feature spec is missing {item}.` |

#### 2C.4 — Gate decision

**If ANY constitution violation is found** (not warnings — only hard violations of core principles):

```
=== Constitution Governance Gate — Cannot Proceed ===

The feature spec violates {N} constitution principle(s):

  1. VIOLATION: {description of conflict}
     Principle: "{principle text}"
     Impact: {what happens if the plan proceeds with this violation}

  2. VIOLATION: {description}
     Principle: "{principle text}"
     Impact: {impact}

Resolve these violations in the feature spec before generating the
implementation plan. Either update the spec to comply with the
constitution, or amend the constitution if the principle needs to change.
```

**WAIT for user response.** Do not proceed with plan generation until violations are resolved.

**If only warnings are found:** log them and proceed. Include the warnings in the plan's "Additional Considerations" section.

**If no constitution exists or no issues found:** proceed to Step 3.

### Step 3 — Load Project Context

Read the following files to understand the project architecture, conventions, and domain model:

| File | Purpose |
|---|---|
| `AGENTS.md` (workspace root) | Workspace layout, project summaries, tech stack, build commands, architecture patterns, commit conventions |
| `ai/knowledge/technical-spec.md` | Full architecture, module dependencies, messaging topics, database config, security, deployment |
| `ai/knowledge/data-model-spec.md` | All database collections/tables, field definitions, indexes, embedded types, enumerations |
| `ai/knowledge/api-spec.md` | Every REST endpoint — method, path, headers, request/response DTOs |
| `ai/knowledge/functional-spec.md` | All features & use cases, business rules, functional flows, actors & roles |
| `ai/knowledge/flows/*.md` | 11 detailed Mermaid flow diagrams for registration, expansion, reduction, TLA, upgrade, deregistration |
| `ai/knowledge/data/*.json` | Sample JSON requests/responses, product model configs, offer configs |

**Cross-reference** the feature spec's impacted areas against the POD Knowledge to identify:
- Which project(s) are affected (consult `AGENTS.md` for the project list)
- Which module(s) within each project
- Which API endpoint(s) are involved
- Which database collection(s)/table(s) and fields are read/written
- Which messaging topics are published to or consumed from
- Which flow(s) from `flows/` are relevant

### Step 4 — Deep-Dive Codebase Analysis

This is the most critical step. You must trace the **actual code** — not just the specs — to understand exactly what exists, what needs to change, and what must not break. Read real source files, note exact line numbers, and document every finding.

#### Step 4.1 — Trace Entry Point

Starting from the API endpoint identified in the feature spec:

1. **Find the entry point class** — search for the HTTP method + path pattern in the relevant project's route/controller files.
   
   **Architecture pattern**: Consult `AGENTS.md` for the project's architecture patterns (e.g. layered architecture, handler→service→repository, MVC controllers, etc.). Trace how existing features implement the same pattern — this is your blueprint.

2. **Trace the full call chain**: Entry Point → Handler/Controller → Service → Repository.
   - Read the entry point to find which handler/controller method is invoked.
   - Read the handler/controller method to find which service method is called.
   - Read the service method **in its entirety** — this is where business logic lives.
   - Note any repository calls (database reads/writes).

3. **Document the chain** with exact file paths and line numbers:
   ```
   Entry Point: {EntryPointClass} → {method}() line {N} → {HTTP_METHOD} {path}
   Handler:     {HandlerClass} → {method}() line {N}
   Service:     {ServiceClass} → {method}() line {N}
   Repository:  {RepositoryClass} → {method}() (database access)
   ```

#### Step 4.2 — Analyse Existing Logic

For each service method that will be modified:

1. **Read the full method** — do not skim. Read every line from method start to method end.
2. **Note the line range** (e.g. `{methodName}()` spans lines {start}–{end}).
3. **Map the branching logic** — identify every `if`/`else`/`switch` branch, what conditions trigger them, and what each branch does.
4. **Identify the insertion point** — where in the method should the new feature branch go? Before which existing branch? After which validation?
5. **Note validation calls** — what validators are invoked, what do they check, will the new feature pass them?
6. **Note mapper calls** — what DTOs are built, which mapper methods are used, what fields are set?
7. **Note side effects** — event messaging (outbox), audit logging, response signing/security, cache operations.
8. **Note async/reactive chain structure** — the project's async/reactive chain patterns (consult `AGENTS.md`). The new code must integrate seamlessly into the existing chain patterns.

#### Step 4.3 — Analyse DTOs and Entities

Check whether the feature requires changes to:

1. **Request DTOs** — does the existing request DTO already have the required fields? If a new field is needed, document the DTO class, its current fields, and what to add.
2. **Response DTOs** — same analysis for response shapes.
3. **Database Entities** — does the entity already have the required fields? If a new field or index is needed, document the entity class and the change.
4. **Enums** — are new enum values needed?
5. **Mapper interfaces** (the project's mapper library) — do existing mappers handle the new fields automatically, or do they need explicit mappings?

**IMPORTANT**: If NO schema changes are needed, **explicitly state this** in the plan:
```
No DTO schema changes needed — {field} already exists on {DtoClass}.
No entity changes needed — {field} already exists on {EntityClass}.
No router changes — reuses existing {METHOD} {PATH} endpoint.
```

This prevents the implementer from making unnecessary changes.

#### Step 4.4 — Check Cross-Cutting Concerns

For every feature, verify these cross-cutting concerns.

**Cross-cutting concerns**: Consult `AGENTS.md` and `technical-spec.md` for cross-cutting patterns:
- Response signing/security (if applicable)
- Event publishing / messaging patterns (if applicable)
- Audit logging patterns
- Correlation ID / distributed tracing propagation
- Error handling patterns

| Concern | What to Check | Where to Look |
|---|---|---|
| **Response Signing/Security** | Does the response need to be signed or have security applied? | Service method — look for security/signing calls near the end of the method. Consult `AGENTS.md`. |
| **Audit / Transaction Event** | Must a transaction event be published to the event messaging system? Most write operations publish using the outbox pattern. | Service method — look for context builder or event publishing calls. Also check the outbox collection/table in `data-model-spec.md`. |
| **Messaging Outbox** | Is the outbox pattern used? If so, the event is written to the database atomically with the entity save, then published asynchronously. | Look for outbox persistence patterns in the service method. |
| **Integrations Layer** | Does the request flow through an integrations/gateway layer before reaching the core service? If yes, trace the integrations service method to confirm the new feature won't cause failures there. | Consult `AGENTS.md` for the integration layer's location — trace the corresponding method. |
| **Correlation ID** | Is the correlation ID propagated? All async/reactive chains should carry a correlation ID via the project's propagation mechanism. | Handler method — look for correlation ID propagation patterns. |
| **Error Handling** | What errors can the new code throw? Are they mapped to the project's error handling pattern (consult `AGENTS.md`)? | Look for existing error/exception throws in the same service method and follow the pattern. |
| **Backward Compatibility** | Will existing flows (other `if`/`else` branches in the same method) still work identically? | Map every branch in the method and confirm the new branch is additive — it must not change the condition or behaviour of any existing branch. |

#### Step 4.5 — Analyse Test Infrastructure

For each project that will be modified:

1. **Find the unit test class** for the service being modified:
   - Find the test in the project's test directory structure (consult `AGENTS.md` for conventions).
   - Note the total line count, the project's test framework annotations, and the project's assertion patterns.

2. **Find the test helper class**:
   - Find existing test helper classes in the project's test directories.
   - Note which factory methods exist for building test DTOs (e.g. `{factory method for test data}` at line ~{N}).
   - Determine if a new factory method is needed for the feature.

3. **Find the E2E test class** (or identify which existing E2E test to model after):
   - Find the E2E tests in the project's E2E test directory (consult `AGENTS.md`).
   - Note the project's E2E test base class, the test lifecycle, and the client used for API calls (e.g. `{domain client method}`).

4. **Note test patterns** — how existing tests mock dependencies, set up data, and assert results. The new tests must follow the same patterns exactly.

#### Step 4.6 — Identify Open Questions and Discrepancies

Compare the feature spec against the actual codebase. Flag any discrepancies:

- Feature spec says field X exists, but it doesn't (or it's named differently).
- Feature spec assumes a certain code path, but the actual branching is different.
- Feature spec references a method that has been refactored or renamed.
- Feature spec doesn't address an edge case that the existing code handles.
- Ambiguities in merge/update semantics that could be interpreted multiple ways.

These become **Open Questions — Resolve Before Coding** in the implementation plan.

### Step 5 — Generate Implementation Plan

Create the file `ai/specs/{ISSUE_ID}/plan.md` with the following structure. **Every section must be filled in with concrete, specific details from Steps 2–4.** Do not use placeholders or generic instructions.

#### Section 5.1 — Header

```markdown
# Implementation Plan — {ISSUE_ID}: {Feature Title}
```

#### Section 5.2 — Prompt Section

This is the core of the plan. It must be **completely self-contained** — an AI coding agent reading ONLY this section (plus the referenced feature spec) must be able to implement the feature without asking any questions.

```markdown
## Prompt

Implement {ISSUE_ID}: "{Feature Title}"

Read the full feature spec at: ai/specs/{ISSUE_ID}/specs.md

## Context

{Write 1–3 paragraphs summarizing:
- What the feature does (in concrete terms)
- Which API endpoint is involved
- What the expected input/output looks like
- What the key technical challenge is (e.g. merge semantics, new branch in existing method, new event type)
- Reference example request/response JSONs in ai/knowledge/data/ if they exist}
```

##### 5.2.1 — Example Request & Response (if applicable)

```markdown
## Example Request & Response

See the real examples in `ai/knowledge/data/` for exact shapes:

**Request** (`{request-filename}.json`):
  {Abbreviated example showing key fields — enough to understand the shape}
  Note: {what's notable about this request — what's present, what's absent}

**Response** (`{response-filename}.json`):
  {Abbreviated example showing key response fields}
  Note: {what's notable — merged fields, injected fields, preserved fields}

Also reference:
  - `{other-file}.json` — {why it's relevant}
```

##### 5.2.2 — Key Business Rules / Merge Strategy / Logic (feature-specific)

```markdown
## {Feature-Specific Section Title} (e.g. "Merge Strategy", "Routing Logic", "Event Schema")

{Detail the core business logic in precise, unambiguous terms.
Use numbered rules, examples, and edge cases.
This section varies per feature — it captures whatever the critical
domain logic is that the implementer MUST get right.}
```

##### 5.2.3 — Open Questions — Resolve Before Coding

```markdown
## Open Questions — Resolve Before Coding

{List any unresolved questions from Step 4.6. For each:
- State the question clearly
- Explain why it matters (what goes wrong if answered incorrectly)
- Suggest a default answer if one is safe
- If all questions are resolved, state: "All open questions have been resolved. No blockers remain."}
```

##### 5.2.4 — Files to Modify

```markdown
## Files to Modify ({project-name} project only)

1. **{ClassName}**
   Path: Follow the project's package/module conventions (see `AGENTS.md`)
   - {What to add or modify — be specific:}
     - Add: `public static boolean methodName(ParamType param)` — {what it does, what it returns, edge cases}
     - Modify: `existingMethod()` (line {N}) — {what to change, where to insert, what condition to add}
   - {Connection to other changes:} This is called by {OtherClass}.{otherMethod}() in change #2.
   - {Important details:} Must short-circuit BEFORE {specific code at line N} to avoid {specific failure}.

2. **{ClassName2}**
   Path: `{module}/src/.../{ClassName2}` (follow project conventions)
   - In `{methodName}()` (~line {N}): {describe the change with pseudo-code if helpful}
     ```
     if (condition) {
         // 1. Step one — {description}
         // 2. Step two — {description}
         // 3. Step three — {description}
     }
     ```
   - This branch must {specific constraint — e.g. "execute BEFORE the entitlement fetch at line 2913"}
   - MUST still: {list all side effects that must be preserved — signing, audit, messaging, etc.}

3. **{ClassName3}** (or {AlternativeClass})
   Path: `{module}/src/.../{ClassName3}` (follow project conventions)
   - Add: `{methodSignature}` — {detailed description of logic}
   - {How it integrates with existing code}
```

Each file entry must include:
- **Full relative path** from the project root
- **Exact method names** to add or modify
- **Line numbers** (approximate is OK, prefix with `~`)
- **What to change** in concrete terms (not "update the logic" — say exactly what logic)
- **Connections** to other files being changed
- **Constraints** specific to that file

##### 5.2.5 — Files NOT to Modify

```markdown
## Files NOT to Modify

- {Explicit statement for each category that does NOT need changes:}
- No DTO schema changes needed — `{fieldName}` ({type}) already exists on both `{RequestDto}` and `{ResponseDto}`.
- No router changes — reuses existing `{METHOD} {PATH}` endpoint.
- No {other-project} changes needed — {explanation of why, with specific code reference showing it will work as-is}.
  {e.g. "the integration service at {ServiceClass}.{method}() checks conditions X and Y; when both are false, it delegates to the core service directly."}
```

This section is critical for **preventing scope creep**. Be explicit about what is out of scope and why.

```markdown

1. **Write unit tests FIRST** (TDD) in:
   The project's test directory for the service being modified (see `AGENTS.md` for test directory conventions).

   - Uses the project's test framework annotations (see `AGENTS.md`)
   - Uses the project's assertion patterns (see `AGENTS.md`)
   - Uses `{TestHelper class}` for building test DTOs

   The project's test helper directory (see `AGENTS.md`)
   e.g., `{newFactoryMethodSignature}`
   that returns {description of what the factory method builds}.
   
   Tests to write:
   a) `{testMethodName_scenario_expected}` — {description: what input, what expected output, what to verify}
   b) `{testMethodName_scenario_expected}` — {description}
   c) `{testMethodName_scenario_expected}` — {description}
   d) `{testMethodName_scenario_expected}` — {description}
   e) `{testMethodName_scenario_expected}` — {description}
   f) `{testMethodName_scenario_expected}` — {description}
   g) Verify existing tests still pass — run the full test suite

2. **Implement the feature** to make the tests pass.

3. **Run existing unit tests** to confirm no regression:
   ```
   cd {project} && {unit_test_command}  # From AGENTS.md
   ```

4. **Write E2E test** in:
   The project's E2E test directory (see `AGENTS.md`).
   
   Follow the existing E2E pattern (see `{ExampleE2ETest}`):
   - Extend the project's E2E test base class
   - Use the project's integration/E2E test framework annotation
   - Setup: {specific setup steps}
   - Test: {specific test action — call which client method with what parameters}
   - Assert: {specific assertions — what fields to check, what values to expect}
   - Also test: {edge cases to cover in E2E}

5. **Run E2E tests**:
   ```
   cd {project} && {e2e_test_command}  # From AGENTS.md
   ```
```

The test cases listed in step 1 must:
- Cover every Acceptance Criterion from the feature spec
- Cover every branch of the new logic (happy path, edge cases, error cases)
- Cover every Functional Requirement
- Verify side effects (messaging event published, audit recorded, response signed/secured)
- Verify non-interference (existing functionality not broken)
- Include the **exact test method name** (following the project's naming convention)
- Include **what to mock**, **what to assert**, and **what the expected outcome is**

### Step 6 — Validate the Plan (including Cross-Artifact Consistency)

Before writing the final file, perform a systematic validation pass. This step has two parts: (A) internal plan validation and (B) cross-artifact consistency — verifying the plan is fully aligned with the feature spec.

#### 6A — Internal Plan Validation

| Check | How to Validate | Action if Failed |
|---|---|---|
| **All file paths exist** | For every path in "Files to Modify" and "Key Code References", verify the file exists in the codebase using file search. | Fix the path or remove the reference. |
| **All method names exist** | For every method referenced, grep the codebase to confirm it exists with the expected signature. | Fix the method name or note the discrepancy. |
| **All DTO fields exist** | For every DTO field referenced (e.g. `additionalInfo`, `metaData`), read the DTO class and confirm the field and type. | Fix the field name/type or note a required change. |
| **Line numbers are accurate** | For every line number reference, read the file and confirm the referenced code is at or near that line. Prefix with `~` if approximate. | Update the line number. |
| **Implementation order is sound** | Confirm that: (1) tests are written first, (2) the feature implementation order avoids forward references, (3) the build/test commands are correct. | Reorder as needed. |
| **Open questions are flagged** | Every ambiguity or discrepancy found in Step 4.6 is listed in "Open Questions — Resolve Before Coding". | Add missing questions. |
| **Prompt is self-contained** | Re-read the Prompt section (§5.2) as if you know nothing else. Can you implement the feature? If you'd need to ask a question, the plan is incomplete. | Add the missing information. |
| **Cross-cutting concerns covered** | Signing/security, audit/messaging, error handling, backward compat, async/reactive — all addressed in constraints or file changes. | Add missing concern. |
| **Constitution compliance** | If `ai/harness/CONSTITUTION.md` exists, verify every file change, implementation order choice, and constraint in the plan complies with the constitution's core principles, quality gates, and conventions. No plan item should violate a governance rule. | Flag the violation and resolve before finalising the plan. |

#### 6B — Cross-Artifact Consistency (Plan ↔ Feature Spec)

This is a **SpecKit-inspired phase gate** that systematically verifies the implementation plan is consistent with and complete against the feature spec. Re-read `ai/specs/{ISSUE_ID}/specs.md` and perform these checks:

| Check | What to Verify | Action if Failed |
|---|---|---|
| **FR coverage** | Every Functional Requirement (FR-01 through FR-{N}) from the feature spec maps to at least one file change in "Files to Modify". Build a traceability matrix: `FR-{N} → {ClassName}.{methodName}`. | Add the missing file change or document why the FR is already satisfied by existing code. |
| **AC coverage** | Every Acceptance Criterion from the feature spec maps to at least one test case in "Implementation Order". Build a traceability matrix: `AC-{N} → {testMethodName}`. | Add the missing test case. |
| **Scope alignment** | Every item in "Files to Modify" falls within the feature spec's "In Scope" boundaries. No file changes address "Out of Scope" items. | Remove out-of-scope changes or flag scope expansion to the user. |
| **Data model alignment** | All entity/DTO changes in the plan match the data model changes described in the feature spec's "Impacted Areas" section. No undocumented schema changes. | Reconcile — update the plan or note that the feature spec needs amendment. |
| **API contract alignment** | Any API endpoint changes in the plan (new paths, changed request/response shapes) match what the feature spec describes. | Reconcile differences. |
| **Open questions consistency** | All spec-level open questions were resolved in Step 2B. Verify that no NEW open questions emerged during codebase analysis (Step 4.6) that remain unaddressed. Any codebase-analysis questions must appear in "Open Questions — Resolve Before Coding". | Add missing questions. If critical blockers are found, present to user before finalising. |
| **Assumption validation** | All `[AUTO-RESOLVED]` assumptions from the feature spec were confirmed in Step 2B. Now verify them against actual code — if any confirmed assumption contradicts the codebase, flag it as a new open question and present to the user. | Correct the assumption or escalate. |
| **No requirement drift** | The plan doesn't introduce requirements, behaviors, or side effects not present in the feature spec. Every plan item should trace back to an FR, AC, or explicit cross-cutting concern. | Remove extraneous items or note them as "additional improvements" clearly separated from the feature scope. |

```markdown
|---|---|---|---|
| FR-01 | {summary} | `{File}.{method}()` | Covered |

```

If any FR or AC shows status "NOT COVERED", the plan is incomplete — add the missing changes/tests before proceeding.

### Step 7 — Transition JIRA to "Ready for Dev"

After writing the implementation plan, transition the JIRA issue to **Ready for Dev** (or equivalent status) to signal that planning is complete and the feature is ready for development.

#### 7a. Obtain JIRA Credentials

```bash
JIRA_PAT=$(grep JIRA_PAT "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
JIRA_BASE_URL=$(grep JIRA_BASE_URL "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
```

#### 7b. Fetch current issue status

```bash
curl -s -H "Authorization: Bearer $JIRA_PAT" \
  "${JIRA_BASE_URL}/rest/api/2/issue/{ISSUE_ID}?fields=status"
```

Parse `fields.status.name`. If already "Ready for Dev", skip the transition.

#### 7c. Get available transitions and execute

```bash
curl -s -H "Authorization: Bearer $JIRA_PAT" \
  "${JIRA_BASE_URL}/rest/api/2/issue/{ISSUE_ID}/transitions"
```

Find the transition whose `name` matches **"Ready for Dev"** (case-insensitive). Execute it:

```bash
curl -s -X POST \
  -H "Authorization: Bearer $JIRA_PAT" \
  -H "Content-Type: application/json" \
  -d '{"transition": {"id": "<TRANSITION_ID>"}}' \
  "${JIRA_BASE_URL}/rest/api/2/issue/{ISSUE_ID}/transitions"
```

#### 7d. Error handling

JIRA transition failure is **non-blocking**. If the PAT is missing, the API returns an error, or no matching transition exists, log a warning and continue to Step 8. The implementation plan is the primary deliverable.

## Important Rules

1. **Every file path must be verified against the actual codebase.** Do not write paths from memory or from specs alone — search for and read the actual files.
2. **Every method name must be confirmed by reading the source.** Method signatures change; the plan must reflect the current state of the code.
3. **Every line number must come from actually reading the file.** Use `~` prefix for approximate line numbers, but they must be within ±10 lines of the actual location.
4. **The Prompt section must be self-contained.** An AI agent reading only the Prompt section (§5.2) plus the feature spec must be able to implement the feature without additional context.
5. **TDD is mandatory.** The implementation order always starts with writing unit tests. Never skip this.
6. **Be explicit about what NOT to change.** The "Files NOT to Modify" section prevents scope creep and wasted effort.
7. **Flag all ambiguity.** If the feature spec is ambiguous or conflicts with the code, document it as an open question. Do not silently make assumptions.
8. **Follow the output format exactly.** The implementation plan must follow the section structure defined in Step 5. This ensures consistency across all features and makes the plan machine-parseable by downstream workflows.
9. **Reference example data.** If sample JSON files exist in `ai/knowledge/data/` that are relevant to the feature, reference them in the plan. These are invaluable for understanding real data shapes.
10. **Do not include implementation code in the plan.** The plan describes WHAT to change and WHERE — not the actual source code. Pseudo-code or brief inline snippets are acceptable for clarity, but full method implementations belong in the `/execute` step.
