# execute

> End-to-end feature implementation — from JIRA prep through TDD implementation, Git push, Merge Request creation, and MR review comment resolution.

---

## Purpose

This workflow takes a JIRA issue ID and delivers the feature end-to-end. It intelligently detects whether MRs already exist with review comments (re-entry) or whether this is a fresh implementation, then:

1. Prepares the workspace — attaches specs to JIRA, creates feature branches, transitions the issue
2. Loads the implementation plan and feature spec
3. Reads existing code thoroughly
4. Implements the feature following TDD — unit tests first, then code, then integration tests
5. Runs all tests (cross-project verification)
6. Self-reviews code and validates against the spec and acceptance criteria
7. Commits, pushes to Git remotes, and creates Merge Requests
8. Generates a change-summary.md with MR links and a traceability matrix

If MRs already exist with unresolved review comments, the workflow enters the **MR Review Fix Phase** — fetches comments, analyses each one, makes targeted code changes, builds, pushes, and replies to reviewers — then loops back through verification.

---

## Prerequisites

- `local.config` at workspace root contains:
  - `JIRA_PAT` and `JIRA_BASE_URL` — for JIRA REST API
  - `GIT_PAT` — GitLab Personal Access Token with `api` scope (for MR creation, comment queries)
- Implementation plan exists at `ai/specs/{ISSUE_ID}/plan.md`.
- Feature spec exists at `ai/specs/{ISSUE_ID}/specs.md`.
- Feature branches follow the naming convention `develop-{ISSUE_ID}` (e.g. `develop-PROJECT-1234`).
- All Git projects are cloned under `$WORKSPACE_ROOT` with an `origin` remote pointing to a GitLab instance.
- The project's build tool is available on PATH (consult `AGENTS.md` for build commands).
- Network access to the JIRA instance and GitLab remote.

---

## Module-to-Project Mapping

Consult `AGENTS.md` at the workspace root for the module-to-project mapping and build commands. The `AGENTS.md` file (generated by the `create-pod-knowledge` skill) contains:
- Which modules belong to which Git project
- The correct build command for each project
- Test commands (unit, e2e, lint) per project

If `AGENTS.md` does not exist, auto-detect by scanning for build files (`pom.xml`, `package.json`, `build.gradle`, `Cargo.toml`, etc.) in each subdirectory.

## Workflow Steps

### Step 1 — Obtain JIRA Issue ID

Ask the user for the JIRA issue ID if not already provided (e.g. `PROJECT-1234`). This ID drives every subsequent step — file paths, branch names, commit messages, and JIRA updates.

```
ISSUE_ID=PROJECT-XXXX
```

### Step 1A — Detect Existing MRs & Review Comments

Before starting fresh implementation, check whether Merge Requests already exist for this issue with unresolved review comments. This enables re-entry into an ongoing feature.

**1A.1 — Load GitLab PAT:**

```bash
GIT_PAT=$(grep GIT_PAT "$WORKSPACE_ROOT/local.config" | cut -d= -f2)
```

**1A.2 — Scan for open MRs across all workspace projects:**

For each Git project under the workspace root:

```bash
REMOTE_URL=$(git remote get-url origin)
GIT_HOST=$(echo "$REMOTE_URL" | sed 's|https://\([^/]*\)/.*|\1|')
GIT_API_BASE="https://${GIT_HOST}/api/v4"
PROJECT_PATH=$(echo "$REMOTE_URL" | sed 's|https://[^/]*/||; s|\.git$||')
ENCODED_PATH=$(echo "$PROJECT_PATH" | sed 's|/|%2F|g')
```

Query for open MRs with the feature branch:

```
GET ${GIT_API_BASE}/projects/${ENCODED_PATH}/merge_requests?source_branch=develop-{ISSUE_ID}&target_branch=develop&state=opened
```

**1A.3 — Check for unresolved comments:**

If open MRs are found, fetch discussions for each:

```
GET ${GIT_API_BASE}/projects/${ENCODED_PATH}/merge_requests/{MR_IID}/discussions
```

Filter to actionable comments only (ignore system notes, bot notes, already resolved discussions).

**1A.4 — Decision:**

| Condition | Action |
|---|---|
| **MRs exist with unresolved comments** | Jump to the **MR Review Fix Phase** at the end of this skill |
| **MRs exist with no unresolved comments** | Inform the user — MRs are clean. Ask whether to continue with additional implementation or skip to reporting |
| **No MRs exist** | Continue with fresh implementation (Step 2) |

## Preparation Phase

### Step 2 — Verify Local Artifacts

Check that both required files exist:

```bash
SPEC_DIR="ai/specs/${ISSUE_ID}"
FEATURE_SPEC="${SPEC_DIR}/specs.md"
IMPL_PLAN="${SPEC_DIR}/plan.md"
```

If either file is missing, stop and tell the user to run `create-specs` or `create-plan` first.

### Step 2A — Pre-Implementation Checklist Gate

Before proceeding with any implementation work, verify that the spec and plan are clean — no unresolved items that would cause rework mid-implementation.

#### 2A.1 — Scan feature spec for unresolved items

Read `ai/specs/{ISSUE_ID}/specs.md` and check for:

| Check | What to Scan | STOP if Found |
|---|---|---|
| **Open questions** | §4.9 Open Questions — any item NOT marked `[RESOLVED]` or `[CLOSED]` | YES — questions must be answered before implementation |
| **Unconfirmed assumptions** | §4.9 Auto-Resolved Assumptions — any `[AUTO-RESOLVED]` not yet marked `[CONFIRMED]` | YES — assumptions must be confirmed |
| **Inline placeholders** | Full spec — any `TODO`, `TBD`, `TBC`, or `[OPEN]` markers | YES — placeholders must be filled |
| **Empty sections** | §4.5 FRs, §4.6 ACs, §4.8 Impacted Areas | YES — critical sections must have content |

#### 2A.2 — Scan implementation plan for unresolved items

Read `ai/specs/{ISSUE_ID}/plan.md` and check for:

| Check | What to Scan | STOP if Found |
|---|---|---|
| **Open questions** | "Open Questions — Resolve Before Coding" section — any item not resolved | YES — blockers must be resolved |
| **Incomplete traceability** | Traceability Matrix — any FR or AC with status "NOT COVERED" | YES — coverage gaps must be filled |
| **Missing file paths** | "Files to Modify" — any placeholder paths (e.g., `{path}`, `TBD`) | YES — all paths must be concrete |
| **Constitution warnings** | "Additional Considerations" — any unresolved `ai/harness/CONSTITUTION.md` warnings from plan generation | NO (warnings only) — log and proceed |

#### 2A.3 — Gate verdict

```
=== Pre-Implementation Checklist ===

Feature Spec (specs.md):
  Open questions:           {0 / N found — STOP}
  Unconfirmed assumptions:  {0 / N found — STOP}
  Inline placeholders:      {0 / N found — STOP}
  Empty critical sections:  {0 / N found — STOP}

Implementation Plan (plan.md):
  Open questions:           {0 / N found — STOP}
  Traceability gaps:        {0 / N found — STOP}
  Placeholder paths:        {0 / N found — STOP}
  Constitution warnings:    {0 / N found — logged}

Verdict: READY TO IMPLEMENT / BLOCKED ({N} items to resolve)
```

**If BLOCKED:** list every unresolved item with its location (file + section). Tell the user to resolve them — either by running `/create-specs` or `/create-plan` again, or by editing the files directly. Do NOT proceed with implementation.

**If READY TO IMPLEMENT:** proceed to Step 3.

**Primary Method: Use MCP Tools**

```

mcp2_jira_transition_issue

```

**Curl Fallback Method**

```bash
# Get available transitions

  --header "Authorization: Bearer $JIRA_PAT" \
  "${JIRA_BASE_URL}/rest/api/2/issue/${ISSUE_ID}/transitions")

  --header "Authorization: Bearer $JIRA_PAT" \
```

### Step 5 — Determine Impacted Projects, Rebase & Create Feature Branches

Auto-detect impacted Git projects from the implementation plan's "Files to Modify" section.

**Always include the `ai/` repo** as an impacted project — it receives feature specs (`specs.md`, `plan.md`), the change summary (`change-summary.md`), and potentially `LEARNINGS.md` updates for every feature. Even though `ai/` is not listed in the plan's "Files to Modify" section (which covers source code only), it must have a feature branch `develop-{ISSUE_ID}` created alongside the source projects so that all feature-related changes are tracked on the same branch and can be merged via their own MR.

**Note on Submodules:** Projects are now stored as git submodules under `ai/submodules/`. When working with submodule projects, navigate to `ai/submodules/{project-name}` for git operations.

For each impacted project (source submodules + `ai/`):

1. **Pre-flight checks** — check current branch and working tree status:
   - If on a different feature branch with dirty state: auto-commit WIP with `JIRA#{OTHER_ID}; WIP: save before switching`
   - If on `develop`/`main` with dirty state: ask user to stash or skip
   - If already on `develop-{ISSUE_ID}`: ask user to keep or recreate
2. **Rebase from remote** — for each project: checkout develop, pull latest, create `develop-{ISSUE_ID}`
3. Present the detected project list to the user for confirmation before proceeding

**Submodule Branch Creation Pattern:**
```bash
# First, ensure all submodules are on develop branch (not detached HEAD)
cd ai
git submodule foreach 'git checkout develop || true'
git submodule foreach 'git pull origin develop || true'

# For each submodule:
cd ai/submodules/{project-name}
git checkout develop
git pull origin develop
git checkout -b develop-{ISSUE_ID}

# For parent ai/ repo:
cd ai
git checkout develop
git pull origin develop
git checkout -b develop-{ISSUE_ID}
```

## Implementation Phase

### Step 6 — Load Implementation Plan & Feature Spec

Read both plan files in full:

```
ai/specs/{ISSUE_ID}/plan.md
ai/specs/{ISSUE_ID}/specs.md
```

**Extract and internalise ALL of the following before writing any code:**

| Item | What to extract |
|---|---|
| **Design Decisions** | Architecture choices, merge strategies, data flow, response-only vs persisted fields |
| **Files to Modify** | Every file listed with its full path, what to add/change, and where (line numbers if given) |
| **Files NOT to Modify** | Explicit exclusions — do NOT touch these files under any circumstance |
| **Implementation Order** | The exact sequence the plan prescribes (e.g. tests first, then validator, then service) |
| **Critical Constraints** | Async/reactive patterns (from AGENTS.md and implementation plan), null-handling rules, merge semantics, response-only fields, signing order, event publishing |
| **Test Plan** | Unit test scenarios, E2E test scenarios, test helper methods to create |
| **Key Code References** | Files referenced for context (existing patterns, helper methods, related services) |

**Do NOT proceed until you have fully understood the plan.** If anything is ambiguous, ask the user before implementing.

### Step 6A — Verify Branch Readiness

For each git project that the plan impacts (use the module-to-project mapping above), verify the feature branch created in Step 5 is current:

1. Navigate to the project directory.
2. Verify the current branch is `develop-{ISSUE_ID}`.
3. Verify clean working tree.
4. Pull latest from remote.

If any project fails branch readiness, **STOP and report** — do not attempt to fix branch issues automatically.

### Step 7 — Read Existing Code

**This step is MANDATORY — do NOT skip it under any circumstance.**

Read ALL files systematically before writing a single line of code:

**7.1 — Files to Modify (from the plan)**
- Read each file end-to-end.
- Note actual line numbers for insertion points mentioned in the plan.
- Note imports, package declarations, class structure.
- Note coding patterns: indentation, naming conventions, Javadoc style, annotation usage.

**7.2 — Key Code References (from the plan)**
- Read every file referenced as context (e.g. existing service methods, mapper helpers, DTOs).
- Understand how similar features are implemented in the codebase.
- Note async/reactive patterns used in the codebase.

**7.3 — Existing Tests**
- Read the test class(es) that will be modified.
- Note test framework annotations (`@Test`, `@DisplayName`, `@ExtendWith`, `@MockBean`, etc.).
- Note test helper classes and factory methods.
- Note the assertion library and patterns used in existing tests.
- Read E2E test classes if the plan includes E2E tests.

**7.4 — Related POD Knowledge (if referenced)**
- `ai/knowledge/flows/*.md` — registration logic flows
- `ai/knowledge/api-spec.md` — API contracts
- `ai/knowledge/data-model-spec.md` — entity schemas
- `ai/knowledge/technical-spec.md` — architecture patterns

### Step 8 — Execute Implementation Order

Follow the exact implementation order prescribed in the plan. For each item in the order:

**Task Progress Tracking:** As each implementation item from the plan is completed, update a running task checklist. Maintain an in-memory checklist of all items from the plan's "Implementation Order" section (and "Files to Modify" entries). After completing each item, mark it done:

```
=== Implementation Progress ===

- [x] T-01: Write unit tests for {ServiceClass}
- [x] T-02: Implement {feature} in {ServiceClass}
- [ ] T-03: Write E2E tests
- [ ] T-04: Run cross-project verification

Progress: 2/4 tasks complete (50%)
```

This checklist will be included in the `change-summary.md` at the end of execution (Step 14). If the implementation is interrupted (e.g., build failure, user stop), the checklist provides a clear record of what was completed and what remains.

#### Step 8.1 — Write Unit Tests First (TDD)

Write tests BEFORE writing the implementation code. This is non-negotiable.

1. **Create test helpers first** — factory methods for building test request/response DTOs, mock entities, etc. Add these to the existing test helper class (e.g. `{ExistingTestHelper}`).

2. **Write test methods** matching the exact test scenarios from the plan:
   - Use the same framework annotations as existing tests (`@Test`, `@DisplayName`, etc.).
   - Use the same naming convention as existing tests (e.g. `methodName_scenario_expectedResult`).
   - Use the same assertion library and patterns as existing tests.
   - Mock dependencies using the same patterns as existing tests (`when(...).thenReturn(...)`).
   - Each test should be focused on ONE scenario from the plan.

3. **Compile-check after each test file**:

```bash
cd <project-dir>
{compile_command}  # From AGENTS.md or auto-detected
{test_compile_command}  # From AGENTS.md or auto-detected
```

Tests are expected to FAIL at this point (no implementation yet) — but they must COMPILE.

#### Step 8.2 — Implement Feature

Make code changes exactly as prescribed in the implementation plan:

1. Follow the plan's file-by-file instructions.
2. **After modifying each file**, compile-check immediately:

```bash
{compile_command}  # From AGENTS.md or auto-detected
```

3. **Match code style exactly:**
   - Same indentation (spaces vs tabs, indent width).
   - Same import ordering and grouping.
   - Same Javadoc and inline comment style.
   - Same logging patterns (`log.info()`, `log.debug()`, `log.error()`).
   - Same async/reactive chain style and patterns.

4. **Follow critical constraints from the plan:**
   - Follow all coding patterns and constraints specified in the implementation plan.
   - Follow the project's async/reactive patterns (if applicable) — consult `AGENTS.md`.
   - Honour null-handling, merge semantics, and field-visibility rules from the plan.
   - Honour event publishing and audit patterns from the plan.

5. **Do NOT modify files listed in "Files NOT to Modify"** — even if it seems like a good idea. If a change seems necessary in an excluded file, STOP and ask the user.

#### Step 8.3 — Run Unit Tests

After implementation is complete, run unit tests for the impacted module:

```bash
cd <project-dir>
{unit_test_command}  # From AGENTS.md
```

**If tests fail:**

1. Read the full test output carefully.
2. **Distinguish between new test failures and regressions:**
   - New test failures (tests you just wrote) → fix the IMPLEMENTATION, not the tests.
   - Regression failures (pre-existing tests now failing) → you likely broke something — review your changes.
3. Fix the issue.
4. Re-run tests.
5. **Retry up to 3 times.** If still failing after 3 attempts, STOP and report the failure to the user with:
   - The exact test(s) failing
   - The error message / stack trace
   - What you've tried so far
   - Your hypothesis about the root cause

#### Step 8.4 — Write Integration / E2E Tests

If the implementation plan specifies E2E tests:

1. Read existing E2E test classes for patterns.
2. Write E2E tests using the same framework and conventions.
3. E2E tests typically hit the running application via HTTP — note the test infrastructure (e.g. `@SpringBootTest(webEnvironment = WebEnvironment.RANDOM_PORT)`, `WebTestClient`).

If the plan does NOT include E2E tests, skip this step and note it in the change summary.

#### Step 8.5 — Run Integration / E2E Tests

```bash
cd <project-dir>
{verify_command}  # From AGENTS.md
```

Apply the same failure handling as Step 8.3 (3 retries, then report).

#### Step 8.6 — Cross-Project Verification (Pre-Push Quality Gate)

Run the **full test suite** across every impacted project (not just the module being modified) to catch cross-module regressions. This is the final quality gate before code is considered ready to push.

##### 8.6.1 — Load Test Configuration

Read the `AGENTS.md` file at the workspace root (if it exists) and look for a **Test Commands Reference** table. This table is the single source of truth for all test commands.

Parse the table to build a lookup: for each impacted project, extract its test entries grouped by type (`unit`, `e2e`, `lint`, `build`).

If `AGENTS.md` does not exist or has no Test Commands Reference, fall back to these defaults:
- Projects with `mvnw`: `./mvnw clean install`
- Projects with `pom.xml`: `mvn clean install`
- Projects with `package.json`: `npm install && npm test`

##### 8.6.2 — Run Full Unit Tests

For each impacted project (not just the module — the full project), run the `unit` type command from the test configuration:

```bash
cd {WORKSPACE_ROOT}/{project_directory}
{unit_test_command}
```

Execute projects **sequentially** (not in parallel) to keep output clean and isolate failures.

**On unit test failure:**

1. Read the full failure output carefully.
2. **Distinguish between new test failures and regressions:**
   - New test failures (tests you just wrote) → fix the IMPLEMENTATION, not the tests.
   - Regression failures (pre-existing tests now failing) → you likely broke something — review your changes.
3. Fix the issue and re-run.
4. **Retry up to 3 times.** If still failing after 3 attempts, STOP and report the failure to the user with:
   - The exact test(s) failing
   - The error message / stack trace
   - What you've tried so far
   - Your hypothesis about the root cause

Continue to the next project regardless of failure — run ALL projects, then report aggregate results.

##### 8.6.3 — Run Lint / Static Analysis (if configured)

For each impacted project that has a `lint` type entry in the test configuration:

```bash
cd {WORKSPACE_ROOT}/{project_directory}
{lint_command}
```

Lint failures are **warnings**, not blockers. Report them but do not stop the workflow.

##### 8.6.4 — Run E2E Tests (conditional)

E2E tests are **only run** when one of these conditions is true:
1. The user explicitly requests E2E tests.
2. The implementation plan specifies E2E tests (check `ai/specs/{ISSUE_ID}/plan.md` for an "E2E" or "End-to-End" section).

If none of these conditions are met, **skip E2E tests** and note it in the report.

**Pre-requisites:** E2E tests typically require a running service instance. Before executing:
1. Check if the service is already running (health check or port check).
2. If not running, inform the user and provide the start command.
3. If the service cannot be started, skip E2E tests and note the reason.

For each impacted project with an `e2e` type entry:

```bash
cd {WORKSPACE_ROOT}/{project_directory}
{e2e_test_command}
```

##### 8.6.5 — Aggregate Verification Report

Produce a structured summary before proceeding:

```
=== Cross-Project Verification Summary ===

| # | Project            | Unit Tests | Lint   | E2E Tests | Status  |
|---|--------------------|------------|--------|-----------|---------|
| 1 | project-alpha      | PASS       | N/A    | SKIP      | OK      |
| 2 | project-beta       | PASS       | PASS   | SKIP      | OK      |

Overall: 2 PASSED / 0 FAILED / 0 SKIPPED
```

**Verdict:**
- **ALL PASS** → proceed to self-review (Step 9) and post-implementation validation (Step 10).
- **FAILURES EXIST** → fix the issues and re-run verification. Do NOT proceed to commit with failing tests.
- **ONLY LINT WARNINGS** → proceed (lint failures are non-blocking).

## Review & Validation Phase

### Step 9 — Self-Review

Run `git diff` in each impacted project and review ALL changes:

```bash
cd <project-dir>
git diff
git diff --stat
```

**Check for:**

| Check | Action if Failed |
|---|---|
| **Unintended changes** — files modified that are NOT in the plan | Revert with `git checkout -- <file>` |
| **Missing changes** — files in the plan that were NOT modified | Implement the missing changes |
| **Style consistency** — formatting, imports, naming | Fix to match existing code style |
| **Constraint compliance** — coding patterns and constraints from the plan not followed | Fix violations |
| **Test coverage** — every scenario from the plan has a corresponding test | Add missing tests |
| **No secrets or credentials** — no PATs, passwords, or API keys in the diff | Remove immediately |
| **No debug code** — no `System.out.println`, no commented-out code, no TODO markers that weren't there before | Remove |

### Step 10 — Post-Implementation Validation (Cross-Artifact + AC Self-Reflection)

After self-review, perform a structured validation that verifies the implementation fully satisfies the feature spec and acceptance criteria. This is the **post-coding counterpart** to the pre-coding cross-artifact validation in `create-plan` Step 6B.

#### 10.1 — Re-read the Feature Spec

Re-read `ai/specs/{ISSUE_ID}/specs.md` in full. Extract:
- All Functional Requirements (FR-01 through FR-{N})
- All Acceptance Criteria (verbatim from section 4.6)
- The Scope boundaries (In Scope / Out of Scope)
- Non-Functional Requirements
- Definition of Done checklist

#### 10.2 — Functional Requirements Verification

For each FR in the feature spec, verify it is satisfied by the implementation:

| FR ID | Requirement | Implementation Evidence | Verdict |
|---|---|---|---|
| FR-01 | {requirement text} | {Specific file:method that implements this, or test that verifies it} | PASS / FAIL / PARTIAL |

**How to verify each FR:**
1. Identify which code change(s) address this requirement (trace from the traceability matrix in the implementation plan).
2. Read the actual `git diff` for those files and confirm the change is present and correct.
3. Check that a unit test exists that exercises this specific requirement.

If any FR shows FAIL or PARTIAL, fix the implementation before committing.

#### 10.3 — Acceptance Criteria Self-Reflection

For each Acceptance Criterion, systematically verify it is met:

| AC # | Criterion | Test Evidence | Code Evidence | Verdict |
|---|---|---|---|---|
| AC-1 | {criterion text or Gherkin scenario} | `{testMethodName}` — PASSED | `{File}.{method}()` implements the behavior | MET / NOT MET / PARTIALLY MET |

**How to verify each AC:**
1. If the AC is in Gherkin format (`Given/When/Then`), trace each clause:
   - **Given**: Is the precondition set up correctly in the test?
   - **When**: Does the test exercise the correct action?
   - **Then**: Does the test assert the expected outcome?
2. If the AC is a plain statement, identify the test(s) that prove it.
3. Check that the test actually **passed** in the most recent test run (Step 8.3 or Step 8.6).
4. Check that the implementation code correctly handles the scenario described.

If any AC shows NOT MET or PARTIALLY MET:
- If the implementation is incomplete, go back to Step 8.2 and implement the missing piece.
- If the test is missing, go back to Step 8.1 and write it.
- Re-run tests after any fixes.

#### 10.4 — Scope Boundary Check

Verify the implementation stays within scope:
1. **No out-of-scope changes**: Review `git diff --stat` — every changed file should relate to the feature spec's "In Scope" items.

## MR Review Fix Phase

This phase is entered automatically when Step 1A detects open MRs with unresolved review comments. It fetches reviewer feedback, makes targeted code changes, and pushes updates back to the MRs.

### Step R1 — Fetch MR Discussions

For each MR found in Step 1A, fetch discussions:

```
GET ${GIT_API_BASE}/projects/${ENCODED_PATH}/merge_requests/{MR_IID}/discussions
```

**Filter to actionable comments only.** Ignore:
- System notes (`"system": true`)
- Bot/CI notes (author `svc_prdmrvalidator` or similar)
- Already resolved discussions (`"resolved": true`)
- Purely informational notes ("mentioned in merge request", "assigned to", etc.)

**Collect for each actionable comment:**

| Field | Source |
|---|---|
| `discussion_id` | `discussion.id` |
| `note_id` | `note.id` |
| `author` | `note.author.username` |
| `body` | `note.body` (the actual comment text) |
| `type` | `note.type` — `"DiffNote"` (inline) or `"DiscussionNote"` (general) |
| `file_path` | `note.position.new_path` (only for `DiffNote`) |
| `line` | `note.position.new_line` or `old_line` (only for `DiffNote`) |

### Step R2 — Fetch MR Diff for Context

For each MR, fetch the changes to understand what was modified:

```
GET ${GIT_API_BASE}/projects/${ENCODED_PATH}/merge_requests/{MR_IID}/changes
```

This returns the `changes[]` array with `old_path`, `new_path`, and `diff` for each file.

### Step R3 — Analyse Each Comment (Accept or Reject)

For each actionable comment:

1. **Read the comment body** carefully.
2. **If it's a `DiffNote`** (inline comment):
   - Read the referenced file at the specified line(s) in the local working tree.
   - Understand the surrounding code context (read 50+ lines around the target).
   - Read related files if the comment references other classes/methods.
3. **If it's a `DiscussionNote`** (general comment):
   - Read the MR description and full diff to understand the scope.
   - Determine which files are relevant to the feedback.
4. **Consult POD knowledge if needed**:
   - `ai/knowledge/flows/*.md`, `api-spec.md`, `data-model-spec.md`
   - `ai/specs/{ISSUE_ID}/specs.md`
5. **Decide**:
   - **Accept** — the comment points out a valid issue, improvement, or missing case. Implement the change.
   - **Reject** — the comment is based on a misunderstanding, is already handled, or conflicts with requirements. Prepare a clear reply explaining why.

### Step R4 — Update Implementation Plan

If review comments require changes that affect the implementation approach, update the implementation plan (`ai/specs/{ISSUE_ID}/plan.md`) to reflect the reviewer's feedback before making code changes. This keeps the plan as the source of truth.

### Step R5 — Make Code Changes & Run Tests

For each accepted comment:

1. Ensure you're on the correct feature branch: `git checkout develop-{ISSUE_ID}`
2. Pull latest: `git pull origin develop-{ISSUE_ID}`
3. Make the code changes following existing conventions.
4. If the comment spans multiple related changes, batch them logically.

After all changes for a project are complete, build and run full unit tests:

```bash

{build_and_test_command}  # From AGENTS.md
```

**This must pass.** If the build fails, fix the issue and re-run until it passes.

## Error Recovery

| Error | Recovery Strategy |
|---|---|
| **Compilation error loop** | Fix and retry up to 3 attempts. If still failing after 3 attempts, STOP and present the error to the user with full context. Do NOT keep looping. |
| **Test failure loop** | Add targeted logging (`log.debug`) to narrow the issue. Distinguish new failures from regressions. Fix implementation, not tests. Retry up to 3 attempts, then STOP and report. |
| **Scope creep** | If the implementation requires changes to files NOT in the plan, or the plan seems incomplete, STOP immediately and ask the user. Do NOT make unplanned changes. |
| **Missing dependency** | If a class, method, or module referenced in the plan doesn't exist, search the codebase first (`grep`, `find`). If genuinely missing, STOP and ask the user. |
| **Merge conflict** | If `git pull` produces merge conflicts, STOP and report the conflicting files. Do NOT attempt automatic resolution. |
| **JIRA API failure** | Treat as non-blocking. Report the failure (HTTP status, response body) but do NOT roll back code changes. The user can update JIRA manually. |
| **Build timeout** | If the full build runs for more than 10 minutes without progress, check for hung tests or infinite loops. Report to the user. |
| **Git push rejected** | For non-fast-forward: offer `--force-with-lease` or `--rebase`. For auth errors: report and skip. For network: retry once. |
| **MR creation failed** | Report the error. Suggest manual creation via GitLab UI: `https://{git-host}/{path}/-/merge_requests/new?merge_request[source_branch]=develop-{ISSUE_ID}&merge_request[target_branch]=develop` |
| **MR comment large arch change** | If a review comment asks for a large architectural change, flag it for human review rather than implementing — reply on the MR explaining it needs discussion. |

## Important Rules

1. **TDD is mandatory.** Write tests BEFORE implementation. Tests must compile (but are expected to fail) before you write the feature code.
2. **Follow the project's coding patterns.** Consult `AGENTS.md` for async/reactive constraints and coding standards.
3. **Read before writing.** Step 7 (Read Existing Code) is not optional. You must read every file before modifying it.
4. **Follow the plan exactly.** Do not add features, refactor unrelated code, or "improve" things not in scope.
5. **Do not modify excluded files.** If the plan says "Files NOT to Modify", those files are off-limits.
6. **Commit message format is enforced.** Follow the format in `AGENTS.md` (e.g. `JIRA#{ISSUE_ID}; description`), typically enforced by the Git hosting pre-receive hook.
7. **Fix implementation, not tests.** If TDD tests fail after implementation, the implementation is wrong — not the tests.
8. **Preserve existing code style.** Match indentation, imports, naming, Javadoc, and reactive chain patterns exactly.
9. **JIRA failures are non-blocking.** Never roll back code changes because of a JIRA API error.
10. **Never force-push.** Always use regular `git push`. If rejected, offer `--force-with-lease` or rebase.
11. **Target branch is always `develop`.** NEVER use `main` or `master` as the MR target branch.
12. **Do not modify files unrelated to review comments** when in the MR Review Fix Phase. Stay scoped.
13. **Do not resolve rejected discussions.** Only resolve accepted ones after replying with the fix.
